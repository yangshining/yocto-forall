## Configuration Ownership

Reusable Xilinx policy is selected by `platforms/xilinx-zynqmp/conf/local.conf.fragment`:

```bitbake
PREFERRED_PROVIDER_virtual/kernel = "linux-xlnx"
PREFERRED_PROVIDER_virtual/dtb = "device-tree"
EXTRA_IMAGEDEPENDS += "device-tree"
XILINX_WITH_ESW = "xsct"
```

The Product Integration owns the concrete hardware input in `products/xilinx-zynqmp-harp-dfe/conf/local.conf.fragment`:

```bitbake
USE_XSCT_TARBALL = "1"
HDF_MACHINE = "${MACHINE}"
HDF_BASE = "file://"
HDF_PATH = "${YOCTO_FORALL_REPO_ROOT}/products/xilinx-zynqmp-harp-dfe/hardware/system.xsa"
```

The path uses `YOCTO_FORALL_REPO_ROOT`, generated by `configs/setup-env.sh`, so it is independent of the build directory.

## Processing Flow

```text
system.xsa
    |
    v
external-hdf / virtual-hdf deployment
    |
    v
Xilinx XSCT/HSI device-tree flow
    |
    +--> generated PS/PL device-tree sources
    +--> product system-user.dtsi and system-conf.dtsi
    |
    v
system.dtb and dependent boot artifacts
```

The Product Integration always appends both device-tree fragments through:

```text
products/xilinx-zynqmp-harp-dfe/
  meta-xilinx-zynqmp-harp-dfe/
    recipes-bsp/device-tree/
      device-tree.bbappend
      files/system-user.dtsi
      files/system-conf.dtsi
```

These files contain product memory, QSPI, network, SPI, PL, and boot-argument policy. They are not generic ZynqMP defaults.

## Updating the XSA

1. Export a hardware handoff for the exact HARP DFE XCZU67DR design.
2. Confirm the device, top module, generator version, and archive contents before replacing the file.
3. Decide explicitly whether the export should contain a bitstream. The current archive does not.
4. Replace only `products/xilinx-zynqmp-harp-dfe/hardware/system.xsa`.
5. Re-run registry, parse, targeted recipe, and image validation.

```bash
. configs/setup-env.sh -V
. configs/setup-env.sh -T harp-dfe-xczu67dr -p scarthgap
bitbake -c cleansstate external-hdf device-tree fsbl-firmware pmu-firmware
bitbake external-hdf device-tree fsbl-firmware pmu-firmware
bitbake petalinux-image-minimal
```

An XSA update can change generated node names and invalidate product DTS references. Treat successful parsing as the first check, not the final check.

## Troubleshooting

| Symptom | Check |
|---|---|
| XSA cannot be found | Run setup again and inspect `HDF_PATH` with `bitbake-getvar --value HDF_PATH`. |
| Hardware design cannot be opened | Inspect `xsa.json`, confirm the archive is intact, and verify tool-version compatibility. |
| Product DTS label is missing | Compare the generated DTS from the new XSA with references in `system-user.dtsi`. |
| XSCT deprecation warning | The current Scarthgap Xilinx adapter still selects XSCT. A future SDT migration requires a separate reviewed change. |
| Kernel stalls while probing PL | Follow [Kernel-stall investigation](KERNEL_HANG_SOLUTION.md); do not assume parsing proves the PL is programmed. |

For bitstream-loading experiments, see [Manual U-Boot FPGA loading validation](UBOOT_FPGA_LOADING_GUIDE.md).
